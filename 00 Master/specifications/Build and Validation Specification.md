# Build and Validation Specification

## Build Workflow

- `python3 "80 Build/build.py"` is the normal full development build. It regenerates responsive HTML cards, field-guide HTML, local workflow HTML guides, the canonical merged web/PWA bundle, `docs/`, and reports; retired card PNG folders, stale optional PDF folders, and optional `Build Output/website/` staging are removed. Without extra flags, it automatically includes each complete, current, machine-local prepared workbook family and preserves exact compatible committed releases for any remaining family. It does not regenerate workbooks or invoke Apple Numbers. If a committed workbook family no longer matches its current source fingerprint or revision and no valid prepared replacement exists, the build stops and requires that family to be rebuilt. The build does not change publish metadata, commit, push, or deploy.
- `python3 "80 Build/validator.py" --source-only` is the pre-build check for editable source. It excludes prepared/published spreadsheet freshness, generated guide agreement, generated build output, and merged-PWA checks that can be expected to be stale before generation. The normal local sequence is source-only validation, build, then full validation, joined with `&&` so it stops at the first error.
- `./80 Build/scripts/publish.sh` is the only supported website publishing command. It calculates the candidate version and requires matching curated highlights in `00 Master/release_notes.yaml` before building, committing, or pushing. It then runs an authorized publish-mode build, increments the minor version once by default, generates one timestamp, preserves compatible previously published spreadsheet downloads, commits only `docs/` and finalized publish metadata through a temporary Git index, and pushes to the current branch. `--major-version N` requires `N` to be greater than the current major version and publishes that release as `N.00`; subsequent ordinary publications resume minor increments from that major version.
- Every publication writes a timestamped machine-local log under `Logs/`. After pushing, `publish.sh` must verify that the latest commit advanced the version by one minor or to an explicitly requested major `.00`, the published index displays that version, the commit matches its upstream, and requested spreadsheet files match their prepared hashes. It must print an unmistakable completed/failed result and the log path. Git cleanliness alone is not evidence that publication occurred.
- GitHub Pages serves `main / docs`; therefore any push to `main` containing `docs/` changes can update the live site even if `publish.sh` was not used. Development and handoff commits must not contain `docs/` changes. Intentional Pages changes require explicit authorization and the supported publishing command.
- Development and test threads must never run the publishing script.
- Fixed card PNG exports and the `--png` build/publish option are retired. Source PNG assets, PWA icons, spreadsheet previews, and temporary in-memory rasterization needed to assemble PDFs remain supported.
- `python3 "80 Build/build.py" --pdf` additionally creates current card and appendix PDFs.
- `python3 "80 Build/build.py" --settings-summary` additionally creates a sortable Excel matrix of all authored subject profiles in `Build Output/reports/Subject Settings Matrix.xlsx`. It requires a full build, remains machine-local, and is not published.
- `./80 Build/scripts/build-matrix-downloads.sh` and `./80 Build/scripts/build-setup-downloads.sh` are the dedicated on-demand workbook workflows. Each generates Excel, converts to Apple Numbers, finalizes native header/freeze behavior, and records its own readiness manifest without running the website build. `build-settings-downloads.sh` remains a Matrix compatibility alias.
- `./80 Build/scripts/build-all-spreadsheet-downloads.sh` prepares both workbook families. The matching `prepare-matrix-downloads.sh` and `prepare-setup-downloads.sh` scripts are manual Numbers-conversion fallbacks.
- `./80 Build/scripts/migrate-setup-tracker.sh <earlier.xlsx>` creates a separate machine-local Setup working copy by carrying forward mutable Checklist, C1–C3 Registration, and Sessions values matched by stable identifiers. It never changes the blank publishable master.
- `./80 Build/scripts/publish.sh --matrix-downloads`, `--setup-downloads`, or `--spreadsheet-downloads` replaces the requested, verified workbook families. `--settings-downloads` remains a Matrix compatibility alias. Each option refuses missing, stale, or changed files. A plain publish preserves exact previously published workbook bytes when their recorded source fingerprints remain current; it blocks rather than preserve stale workbooks. `--remove-spreadsheet-downloads` is the explicit removal action.
- `./80 Build/scripts/build-verification-working-copy.sh` generates the machine-local working tracker from current definitions plus `90 Testing/eos_r5_verification_status.yaml`. `import-verification-status.sh` imports approved mutable workbook fields into that Git-tracked YAML. `reconcile-verification-status.sh` preserves history while marking verified results and registration passes for retest when their definition fingerprints changed.
- `./80 Build/scripts/open-verification-working-copy.sh` creates the machine-local tracker only when neither supported format exists, reports whether it has unimported changes, and opens the most recently modified Numbers or Excel copy. The dedicated on-camera verification workflow documents test order, evidence and completion rules, status import, and YAML-based handoff between Macs.
- `python3 "80 Build/verify_publication.py"` verifies the latest publication commit. Finish-day spreadsheet publication requires both `--require-target matrix` and `--require-target setup`, followed by the ordinary Git synchronization report.
- `python3 "80 Build/release_notes.py"` prints curated reader-facing Markdown for the two most recent publications. `--from VERSION` selects an earlier starting publication through the latest release, `--to VERSION` compares the immediately preceding publication with that release, and both options select an exact historical range. Publication boundaries and dates come from valid committed publish-metadata transitions. Every included target release must have curated highlights in `00 Master/release_notes.yaml`; the command never substitutes commit-message or changed-file guesses.
- A change to an established command, workflow, or operator-facing procedure requires review of the relevant `WORKFLOWS` Markdown and `FINISH_DAY.md`. The change proposal must identify any guide updates or state why none are appropriate. Edit workflow Markdown only; regenerate tracked HTML through the normal build or Finish Day.
- `python3 "80 Build/build.py" <profile>` preserves the existing single-profile workflow; run a full build before publishing.
- `python3 "80 Build/build.py" build website` preserves optional web-host staging behavior; `build pages` refreshes the Pages mirror.
- Do not place rendering decisions in profile YAML or change build logic as a side effect of documentation/content work.

## Output and Release Behavior

- Disposable generated artifacts belong in the machine-local workspace's `Build Output/` folder. The default workspace is the sibling folder `<repository name> Local/`; `PRS_LOCAL_WORKSPACE` may set a different absolute or user-relative location.
- `Build Output/merged-build/` is the canonical generated web/PWA bundle. It contains released responsive cards under `Cards/*.html` and copied card assets under `web-assets/`.
- `FINISH_DAY.html` and `WORKFLOWS/*.html` are tracked local project guidance generated from their Markdown sources by normal builds and `finish-day.sh`. They must never be copied into `docs/`.
- `docs/` is an exact publishing mirror for GitHub Pages configured as `main / docs`.
- The published index orders its sections by expected frequency of use: **Subjects**, **Field Guides**, **Camera Setup & Controls**, then **Deep Dive**.
- `Build Output/website/` is optional staging for non-GitHub web hosts. Only the explicit `build website` target creates or retains it; ordinary full builds remove it. When it exists, validation requires it to match the canonical merged build.
- `Build Output/reports/Subject Settings Matrix.xlsx` is an optional machine-local report. Its primary worksheet starts in canonical card order with Menu Location, Best or Quick Access, and Setting followed by editable C1 Wildlife, C2 Birds in Flight, and C3 Landscape columns initialized from the approved registration targets, baseline-derived Default Settings, the unchanged authored subject profiles, Card Order, and Rapid Setup Order. The C1–C3 cells are ordinary values rather than source-switching formulas so they can be edited or replaced during experiments. A separate `C1-C3 Defaults` worksheet preserves the approved target table in the same setting order for restoration; its note row identifies the values as approved targets pending physical verification rather than verified current camera state. Its C1–C3 cells carry transferable relative `not equal` rules and matching hidden helpers so ordinary copy/paste back to the primary sheet restores compatible conditional highlighting instead of replacing it with unformatted cells. The frozen `Compare to:` row provides named-target dropdowns for C1–C3, Default Settings, and every authored subject profile. Every target initially compares with itself, producing an unhighlighted starting view, and may instead compare with any listed target. A frozen `Card starts from:` row immediately below it shows each authored card's `card.field_setup` route, including the starting C1–C3 profile and any named My Menu tab. Differences use the approved pale-yellow `not equal` conditional highlight through one hidden same-sheet helper column per target; use the cell-comparison rule supported by both Excel and Apple Numbers rather than a custom formula-expression rule. The title, sorting instructions, and legend are three visual bands within one removable drawing object above the primary cell table, so no merged cells interfere with assigning header rows after import into Apple Numbers. The comparison row, card-start row, and table header plus columns A:C are frozen in Excel; the verified Numbers companion uses three native frozen header rows and three native frozen header columns with the banner as a separate object above the table. `C1-C3 Defaults` freezes its note and table-header rows plus column A in both formats. Columns A, B, and C use 85-point, 80-point, and 80-point widths respectively. Column A is normal and left-aligned, column B is bold and centered, column C is bold and right-aligned, and every cell in the table header row is bold. Wrapped table rows use automatic height so all generated content is visible and later user edits resize the rows. Metering is included even though the profiles inherit Evaluative from the baseline. My Menu routes use the `MM-` abbreviation, and only proposed tabs carry an asterisk explained in the legend. Separate numeric sort columns provide canonical card order and rapid camera-setup order.
- `Build Output/reports/EOS R5 Setup & Verification Tracker.xlsx` is the blank publishable Setup master and opens on Dashboard. Its Checklist begins with a removable three-band drawing aligned to the table's left edge, freezes the table header plus column A in Excel, and uses one frozen native header row plus frozen native column A in Numbers. Menu, Checklist, C1–C3 Registration, and Sessions table rows use automatic height so wrapped generated content remains visible and later user-entered notes resize their rows. Fixed heights remain only for structural banner and comparison-control rows; merged title and instruction areas retain deliberate sizing because spreadsheet applications do not reliably auto-fit merged cells. Checklist Status is centered; Menu Location is bold and centered. C1–C3 Registration freezes column A in both formats, right-aligns column A, and materializes complete current values for Default Settings, C1, C2, and C3 during every generation. Column B comes directly from the current baseline; each registered-mode target merges that same baseline with only its explicit slot-specific overrides from `eos_r5_verification_tracker.yaml`, so inherited values cannot remain stale after a baseline change. Its frozen third row keeps `Compare to:` visible in column A and provides named-target dropdowns for Default Settings, C1 Wildlife, C2 Birds in Flight, and C3 Landscape. Default compares with itself; C1–C3 initially compare with Default Settings; every target may instead compare with any listed target, including itself. Target differences use the approved pale-yellow conditional highlight through four narrow same-sheet helper columns that expand with the registration table. Dashboard centers populated values in columns B–E and H and retains formula-driven green, amber, and red status cues. Completion displays 100% as green text, partial completion as bold black text on pale yellow, and 0% as italic text. The Menu sheet is the authoritative workbook lookup for Best Access, Menu Location, and Menu Detail; the Checklist derives those fields by formula. SWITCH My Menu configuration occurs before shared setup and profile registration. `Backup-Settings` is a completed checkpoint state used after shared setup/controls and after all three registered modes are read back.
- A verified Numbers companion and a separate content-hash manifest may accompany each Excel report. Both workbook families visibly show their independent workbook revision, shortened source fingerprint, and generation date. When opt-in replacement publication is authorized, the generated site contains the requested Excel/Numbers pairs under **Downloads** and writes a published release manifest with revisions, source fingerprints, stable filenames, and hashes. Normal local builds automatically include valid prepared workbook families and preserve compatible committed releases for the rest; ordinary publications preserve compatible committed releases unless replacement is explicitly requested. Readiness manifests, verification status, working copies, and import markers are never published.
- On C1–C3 Registration, three-point project-blue outer borders frame the complete column ranges `A:A`, `B:E`, `F:I`, and `J:M`.
- `90 Testing/eos_r5_verification_status.yaml` is the canonical non-published mutable testing record. Spreadsheet import may change only approved Checklist, C1–C3 result/notes, and Sessions fields. Each verified test and passed registration target records the definition fingerprint it verified. Definition changes preserve evidence/history but invalidate affected passes as needing retest; new tests start unverified and removed tests are archived.
- Timestamped pre-change recovery backups belong under the local workspace's `Backups/` folder, not in the repository.
- Card and field-guide PDFs are opt-in.
- Profile and appendix release flags independently control inclusion in the offline bundle as defined by their specifications.
- Validate generated output before publishing. Publishing remains a manual, explicitly authorized Git operation.

## Computer Handoff

- Complete a unit of work on the computer where it began before continuing it elsewhere.
- Run relevant validation, commit every intentional source change, push the current branch, and verify a clean working tree before handoff.
- Import any changed local verification working tracker into Git-tracked YAML status before committing. `finish-day.sh` must block when the workbook differs from its last successful YAML synchronization.
- If a development build changed tracked `docs/` but publication is not intended, restore `docs/` to the current commit before the final clean-tree check. Disposable local output does not transfer through Git and is rebuilt on the next computer.
- Do not run the publishing workflow merely to move work between computers. Publish only when intentionally updating the live site, version, and timestamp.
- `80 Build/scripts/git-status-report.sh` is the read-only project-state report apart from refreshing remote-tracking references with `git fetch --prune`. It must not pull, merge, commit, push, switch branches, or change project files.
- `80 Build/scripts/preflight-git.sh` uses that report to allow clean synchronized work or identified local work, and to block a clone that is behind, diverged, or cannot be verified safely. It must not update the working branch automatically.
- `80 Build/scripts/finish-day.sh` is an interactive handoff helper. It runs source-only validation, the normal development build, and full validation in that order. It requires confirmation before changing `docs/`, staging, committing, or pushing. When a development build changes `docs/`, it creates a timestamped machine-local recovery archive, restores tracked `docs/` to `HEAD`, removes only archived untracked generated files under `docs/`, verifies that `docs/` is clean, and then stages the remaining source changes. It must refuse to push when an existing unpushed commit contains `docs/` changes, and it must never invoke the publishing workflow.

## Validation Requirements

Run `python3 "80 Build/validator.py"` after relevant changes. It orchestrates validators for:

- project structure (`validators/structure.py`);
- YAML parseability and duplicate keys (`yaml_validator.py`);
- baseline shape (`baseline_validator.py`);
- card-layout structure and required-setting alignment (`card_layout_validator.py`);
- complete, unique access methods and rapid-setup ordering for every subject-summary setting (`setting_access_validator.py`);
- external spreadsheet layout/source requirements (`spreadsheet_spec_validator.py`);
- consistency of prepared workbook-download manifests, published release fingerprints/hashes, and any generated site downloads (`spreadsheet_download_validator.py`);
- canonical verification-status structure and agreement between Verified results and current definition fingerprints (`verification_status_validator.py`);
- curated release-note source structure (`release_notes_validator.py`);
- governing-document presence, local links, stale retired references, and decision statuses (`governance_validator.py`);
- current generated HTML agreement for the finish-day and local workflow guides (`finish_day_guide_validator.py`, `workflow_guides_validator.py`);
- agreement between the two custom-control records, valid five-class control statuses, canonical C1–C3 profile mappings, and canonical setting terminology (`control_validator.py`);
- appendix manifest/content relationships (`appendix_validator.py`);
- profile inheritance and overrides (`profile_validator.py`);
- assets/icons (`icon_validator.py`);
- Canon guide YAML (`canon_guides_validator.py`);
- generated artifacts (`output_validator.py`);
- merged PWA integrity (`pwa_validator.py`);
- supported links (`link_validator.py`).

Generated-output validation also checks responsive viewport metadata, local path portability, referenced HTML assets, released index/card correspondence, duplicate HTML IDs, and unresolved template text.

Run the dedicated `validators/validate_canon_r5_icons.py` when Canon icon reference data/assets change. For documentation consolidation, also search Markdown/YAML/code for stale paths and contradictory normative statements; the project validator does not validate documentation links or rule uniqueness comprehensively.

## Machine-Readable Sources and Enforcement Map

| File | Governs | Primary enforcement |
| --- | --- | --- |
| `00 Master/baseline.yaml` | Shared defaults and camera/workflow context | `baseline_validator.py`, `profile_validator.py`, `yaml_validator.py` |
| `00 Master/schema.yaml` | Intended profile/YAML field structure | `yaml_validator.py`; parts are enforced directly by `profile_validator.py` |
| `00 Master/card_layout.yaml` | Card-row display order plus always-shown rows and labels | `card_layout_validator.py`, `yaml_validator.py`; consumed by rendering/build code, with output review |
| `00 Master/setting_access.yaml` | Best access method, menu location, and rapid-setup order for subject-summary settings | `setting_access_validator.py`, `yaml_validator.py`; consumed by the optional Excel summary build |
| `00 Master/spreadsheet_layouts.yaml` | Shared and workbook-specific spreadsheet dimensions, fonts, banners, column styles, and freeze behavior | `spreadsheet_spec_validator.py`, `yaml_validator.py`; consumed by Matrix and Setup builders |
| `00 Master/release_notes.yaml` | Curated reader-facing highlights keyed by published website version | `release_notes_validator.py`, `yaml_validator.py`; candidate-version coverage enforced by the publish build; consumed by `release_notes.py` |
| `90 Testing/eos_r5_verification_tracker.yaml` | Setup checklist rows, access lookup data, status lists, and C1–C3 registration targets | `spreadsheet_spec_validator.py`, `yaml_validator.py`; consumed by the Setup builder |
| `90 Testing/eos_r5_verification_status.yaml` | Mutable Checklist, C1–C3, session, history, and verification-revision state | `verification_status_validator.py`, `yaml_validator.py`; imported from and rendered into the machine-local working tracker |
| `controls.yaml` and `data/canon_r5_custom_controls_current.yaml` | Verified current controls, approved targets, and canonical C1–C3 profile mappings | `control_validator.py`, `yaml_validator.py` |
| `50 Field Guide/required_appendices.yaml` | Required appendices, sections, relationships, topics, exceptions, release flags | `appendix_validator.py`, rendering/build and PWA validation |

`80 Build/validator.py` is the validation entry point. A passing validator means its implemented checks passed; it does not replace visual card review, documentation-reference review, or review of requirements not yet encoded as checks.
