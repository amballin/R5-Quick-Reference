# Build and Validation Specification

## Build Workflow

- `python3 "80 Build/build.py"` is the normal full development build. It regenerates responsive HTML cards, field-guide HTML, local workflow HTML guides, the canonical merged web/PWA bundle, `docs/`, and reports; retired card PNG folders, stale optional PDF folders, and optional `Build Output/website/` staging are removed. Without extra flags, it automatically includes each complete, current, machine-local prepared workbook family and preserves exact compatible committed releases for any remaining family. It does not regenerate workbooks or invoke Apple Numbers. If one or more local or committed workbook families no longer match their current source fingerprints or revisions, the build reports all stale families together and stops with the exact consolidated refresh command. The build does not change publish metadata, commit, push, or deploy.
- The normal full build also regenerates `Build Output/Card Candidates/index.html`, a machine-local review mini-site containing only profiles whose `metadata.release` is not `true`. Candidate cards retain working local appendix links but remain outside `merged-build`, `docs`, and every publishable mirror. Single-profile builds do not regenerate the complete candidate index.
- Validation must be proportional to the affected surface. Use the narrowest repository-owned check that proves the changed source is valid; add source-only validation when the change participates in shared repository structure or governance. A narrow source change that cannot affect generated output or build behavior does not require a development build.
- `python3 "80 Build/validator.py" --source-only` checks editable source while excluding prepared/published spreadsheet freshness, generated guide agreement, generated build output, and merged-PWA checks that can be expected to be stale before generation. Release-note-only changes require confirmation that the entry is for the next publication version, source-only validation, and diff review. They do not require a development build; publish mode independently requires the exact candidate version before publication.
- Run the normal local sequence—source-only validation, build, then full validation, joined with `&&`—when a change can affect generated cards, appendices, workflow HTML, downloads, search, the merged PWA, `docs/`, or build behavior. Also run it at integration, computer-handoff, and Finish Day checkpoints, or when a validator explicitly requires regenerated output. Publication uses the supported publish-mode build and post-publication verification; when its source inputs are unchanged after a successful Finish Day sequence, do not insert another development build immediately before it.
- One successful full sequence is sufficient when its inputs remain unchanged. Repeat from a clean workspace only when build, rendering, template, spreadsheet-generation, or reproducibility behavior changed; when investigating suspected hidden state or nondeterminism; or when inputs changed or a previous check failed. Routine content and metadata edits must not trigger duplicate full builds merely to satisfy a general durability rule.
- The Profile Editor's **Review & Build** workspace may invoke the existing verification-status importer as a separate, explicitly confirmed action only when the pending-browser-change count is zero. Import is never automatic, uses the most recently modified local Numbers or Excel working tracker under the existing importer rules, is serialized with build requests, and displays the importer output. After an import, readiness must be rerun.
- The Profile Editor's **Camera Lab evidence** review may inventory completed machine-local physical EDSDK guarded-run journals only when the pending-browser-change count is zero. Simulator, incomplete, unmapped, non-registration, and previously promoted evidence must remain ineligible. The first release maps an exact eligible setting path only to the matching C1–C3 registration row for the profile currently assigned to that slot and may set only that slot's `configured` result to `Pass`; existing read-back, registration, operational-test, backup, checklist, and evidence-class states remain unchanged. Selection defaults to empty. Review must block when the working tracker has unimported edits, preserve the method and complete journal provenance in history, bind selected journal hashes plus candidate bytes and source fingerprints to a one-use token, require separate confirmation, create a recovery backup, write canonical status atomically, rebuild the safely synchronized working tracker, run source validation, and restore canonical status plus the working copy on failure.
- The dedicated **Camera Buttons** workspace may change only the fixed existing `controls`/`dials` entries in `controls.yaml` and their synchronized `buttons`/`dials` entries in `data/canon_r5_custom_controls_current.yaml`. It must reject control identity, order, row-count, and C1–C3 mapping changes. Assignment, operation, INFO details, notes, and evidence status are reviewed together; changing an owner-confirmed assignment, operation, or INFO detail forces `approved_target_pending_camera_verification`. Review and save require isolated candidate validation, an exact two-file diff, byte- and fingerprint-bound one-use token, machine-local recovery backup, concurrent-source recheck, atomic writes, source validation, and complete rollback.
- Source validation must require `80 Build/profile_editor/control_options.yaml`, a non-empty Canon default and assignment-choice list plus an official mapped icon for every fixed control/dial, the Camera Buttons draft-preview endpoint, and the approved Daily work → Profile setup → Occasional sidebar order. A control included on the generated card must resolve through the same icon mapping in the editor. Draft preview accepts the same complete candidate structure as review and must use in-memory candidate control data rather than temporarily replacing `controls.yaml`.
- The Profile Editor may move a saved editable profile to the machine-local Deleted Cards holding area only when `metadata.release` is `false`, no unsaved browser draft exists for it, and a complete UUID-based inbound-reference check finds no C1–C3 assignment, `card.field_setup.source_card_id`, appendix `profile_ids`, or other registered structured dependency. The review must report conservative narrative mentions separately, show the complete active-source removal, require explicit confirmation, create a recovery backup, preserve the exact source plus an integrity manifest in Deleted Cards before active removal, detect concurrent changes, validate source afterward, and restore active source automatically on failure. Restore requires an exact addition diff, filename and UUID conflict checks, a backup, validation, and rollback; only a successful restore removes the holding entry. Released profiles, permanent reference cards, and permanent purge remain unavailable through the editor.
- The Profile Editor's **Review & Build** workspace may invoke the normal local sequence with conditional spreadsheet recovery. It must first receive a zero pending-browser-change count and run a fresh readiness check that diagnoses verification, Matrix/settings, and Setup spreadsheet-derived state from authoritative source fingerprints. Safely stale artifacts do not block readiness: the editor reports them before the final confirmation, then runs source-only validation, `build-all-spreadsheet-downloads.sh` only when refresh is needed, the normal development build, and full validation. The confirmed action may launch Apple Numbers. Readiness and the refresh step must block without modifying files when the verification working copy may contain unimported edits. The local build must run as a serialized reconnectable background job that exposes the numbered current stage, exact safe command, elapsed time, bounded expandable command log, completion/failure state, and separate readiness/final status details; browser session storage must reconnect Review & Build after a page refresh. Build and import requests are serialized, the editor stops at the first failing step and reports its output, and it never invokes Git, publication, or version-metadata changes.
- The Profile Editor's **Finish Day** workspace and `80 Build/scripts/finish-day.sh` must use the same implementation in `80 Build/finish_day.py`. Finish Day is serialized with editor build/import actions and requires zero pending browser drafts plus safely classifiable verification state. Browser preparation must start as a reconnectable background job and report the current step, exact safe command, elapsed time, completed steps, and bounded output while retaining every existing workflow guard. Before the normal build, diagnose verification, Matrix/settings, and Setup derived state. When it is safely stale, show the affected families and require a separate visible permission that warns Apple Numbers may open before running the consolidated refresh; when the working tracker may contain unimported edits, block and provide the in-editor tracker-import action. Preparation requires explicit confirmation before source validation, conditional spreadsheet refresh, the normal development build, full validation, and backed-up restoration of generated `docs/`. Commit requires a content-sensitive one-use review token, an exact source-file list that excludes `docs/`, a non-empty message, and separate explicit confirmation. Push requires another explicit confirmation, allows only the current branch's exact same-named upstream on `origin`, rejects outgoing commits containing `docs/`, and must finish with a clean synchronized report. It must never merge, switch branches, change publish metadata, or publish the website.
- The Profile Editor's **Integrate Branch** workspace must use `80 Build/integrate_branch.py`, remain serialized with editor build/import and Finish Day actions, and be available only from a non-main branch with zero pending browser drafts, a clean worktree, and exact synchronization with its same-named `origin` upstream. It must refresh and target only `origin/main`. Browser preparation must use the same reconnectable bounded-progress mechanism as Finish Day. Preparation requires confirmation and must create the proposed merge in a disposable worktree based on current `origin/main`, stop without changing either real branch on conflicts or concurrent movement, and reject any candidate that changes `docs/`. Diagnose spreadsheet-derived state against the exact merged candidate. If it is safely stale, stop with an in-editor recovery choice; only a separately confirmed retry may rebuild the stale artifacts inside a fresh disposable candidate, warn that Apple Numbers may open, and continue. A terminal refresh in the original checkout is not sufficient evidence for the isolated candidate. Then run source validation, the normal development build, and full validation, restore generated `docs/`, and present the exact commits and files with a content-bound review token. Applying the reviewed tree to local `main`, pushing `main`, and fast-forwarding plus pushing the working branch each require separate confirmation and a fresh clean/ref check. Resynchronization must use fast-forward history, never rebase or rewrite published branch history, and may push only the working branch's exact same-named `origin` ref. After a continuous successful resynchronization, compare the persistent Main worktree's installed Profile Editor and Camera Lab wrappers with deterministic candidates and rebuild only missing, invalid, or byte-stale wrappers. Report current, rebuilt, unavailable, or failed app-refresh state separately from Git completion. If merged runtime inputs changed, require an explicit restart notice for any running local apps; never stop an editor or camera session automatically. Never install an app linked to a disposable integration worktree. No integration stage may invoke publication, change publish metadata, create a release, or push another remote.
- The Profile Editor's optional **Cleanup Review** workspace must use `80 Build/cleanup_review.py` and may inventory only exact `.DS_Store` metadata inside the repository plus recognized timestamped workflow backup directories under the configured machine-local `Backups/` folder. Backup grouping must preserve the newest successful recovery directory for each fixed workflow type and each profile operation/target, list only superseded recognized entries, impose no age threshold, and ignore symlinks and unrecognized or manually named backups. Nothing may be selected automatically. The review must show exact path, modified time, size, and reason; deletion requires a current one-use review token, at least one exact selected identifier, and separate permanent-deletion confirmation. Recompute candidate identities immediately before deletion and stop on change. Canonical source, private-profile data, current deliverables, protected newest backups, and automatic temporary-worktree cleanup are outside this feature.
- `python3 "80 Build/baseline_impact_check.py"` is the read-only worktree check for semantic baseline-default changes relative to `HEAD`; `--base-ref REF` selects another Git baseline such as `origin/main`. It uses the same repository-owned impact engine as the Profile Editor, returns 0 when no semantic baseline-default change exists, 1 when review is required, and 2 when the comparison cannot be completed. It is not a migration writer and does not replace the normal validation sequence.
- `./80 Build/scripts/publish.sh` is the only supported website publishing command and runs only from `main`. It must stop before building or changing files on a prototype or detached branch. It calculates the candidate version and requires matching curated highlights in `00 Master/release_notes.yaml` before building, committing, or pushing. It then runs an authorized publish-mode build, increments the minor version once by default, generates one timestamp, preserves compatible previously published spreadsheet downloads, commits only `docs/` and finalized publish metadata through a temporary Git index, and pushes to `main`. `--major-version N` requires `N` to be greater than the current major version and publishes that release as `N.00`; subsequent ordinary publications resume minor increments from that major version.
- Profile Editor's **Release & Publish** workspace must use `80 Build/publication_workflow.py` around that same publisher and must never implement an independent deployment path. Readiness requires zero browser drafts, the Main project editor, clean synchronized `main`, exact `origin/main` tracking, valid spreadsheet diagnostics, and curated notes for the exact selected next minor or new major version. A prototype editor may only launch the checked-out Main project editor. Adding the missing release-note entry requires exact-diff review, a content-sensitive one-use token, a machine-local recovery backup, concurrent-change detection, atomic replacement, source-only validation, and rollback on failure; Finish Day must then commit and push that source change. The final publication review binds the main commit, version, exact spreadsheet build IDs, and automatic/force/remove spreadsheet choice. Automatic is the default: preserve exact verified bytes when current, or rebuild and replace only diagnosed stale families. Force must regenerate and replace both families even when current. Live publication requires a separate confirmation, runs as a serialized reconnectable background job, retains the verification-working-copy safety gate before any automatic or forced workbook generation, calls `publish.sh`, and reports completion only after both the publisher receipt and a clean synchronized Git report pass.
- Every reconnectable guarded-job panel must render terminal state explicitly. While running, it may show the next-command placeholder. On completion, it must show the workflow-specific successful receipt. On failure, it must state that the workflow did not complete, stop the running indicator, preserve the actual exception in the bounded visible log, and never show a running-state placeholder.
- Every editor-visible workflow blocker must pair its plain-language summary with the safest applicable in-editor recovery action. Terminal commands may remain in expandable expert details but must not be the only recovery path. Mutating recovery actions require explicit confirmation and exact safety rechecks. A clean branch that is only behind its exact same-named `origin` upstream may offer a confirmed `--ff-only` update; any local commits, local changes, divergence, conflict, detached checkout, unexpected upstream, identity change, or incomplete rollback must remain non-automatic. When another guarded job owns the serialized workflow lock, return its identity so the editor can reconnect to its existing progress instead of presenting a dead-end stop.
- Every publication writes a timestamped machine-local log under `Logs/`. After pushing, `publish.sh` must verify that the latest commit advanced the version by one minor or to an explicitly requested major `.00`, the published index displays that version, the commit matches its upstream, and requested spreadsheet files match their prepared hashes. It must print an unmistakable completed/failed result and the log path. Git cleanliness alone is not evidence that publication occurred.
- GitHub Pages serves `main / docs`; therefore any push to `main` containing `docs/` changes can update the live site even if `publish.sh` was not used. Development and handoff commits must not contain `docs/` changes. Intentional Pages changes require explicit authorization and the supported publishing command.
- Development and test threads must never run the publishing script.
- Fixed card PNG exports and the `--png` build/publish option are retired. Source PNG assets, PWA icons, spreadsheet previews, and temporary in-memory rasterization needed to assemble PDFs remain supported.
- The macOS application-wrapper build embeds the camera-and-lab icon for R5 Camera Lab and the camera-and-pencil icon for R5 Profile Editor. It uses amber prototype variants outside `main`, green production variants on `main`, and derives each bundle's deterministic `.icns` resource from the authoritative transparent 1024-pixel PNG under `60 Assets/app-icons/`.
- `python3 "80 Build/build.py" --pdf` additionally creates current card and appendix PDFs.
- `python3 "80 Build/build.py" --settings-summary` additionally creates a sortable Excel matrix of all authored subject profiles in `Build Output/reports/Subject Settings Matrix.xlsx`. It requires a full build, remains machine-local, and is not published.
- `./80 Build/scripts/build-matrix-downloads.sh` and `./80 Build/scripts/build-setup-downloads.sh` are the dedicated on-demand workbook workflows. Each generates Excel, converts to Apple Numbers, finalizes native header/freeze behavior, and records its own readiness manifest without running the website build. `build-settings-downloads.sh` remains a Matrix compatibility alias.
- `./80 Build/scripts/build-all-spreadsheet-downloads.sh` is the single non-publishing recovery command for stale spreadsheet-derived state. It diagnoses the verification working copy and both release workbook families before writing anything, blocks if the verification copy may contain unimported edits, then rebuilds only stale safe artifacts in this order: verification working copy, Matrix/settings downloads, Setup downloads. Current artifacts are not rebuilt unless `--force-release-workbooks` is supplied; that option retains the same diagnostic and unimported-edit gates, refreshes a safely stale verification copy when necessary, then regenerates and verifies both release families. The matching `prepare-matrix-downloads.sh` and `prepare-setup-downloads.sh` scripts remain manual Numbers-conversion fallbacks.
- Automatic Numbers operations retain both supported bundle IDs, explicitly launch the discovered Numbers application and wait for AppleScript responsiveness before open, save, export, or finalization operations, and report the result for each candidate if automation fails. No manual Numbers launch is required.
- `./80 Build/scripts/migrate-setup-tracker.sh <earlier.xlsx>` creates a separate machine-local Setup working copy by carrying forward mutable Checklist, C1–C3 Registration, and Sessions values matched by stable identifiers. It never changes the blank publishable master.
- `./80 Build/scripts/publish.sh --matrix-downloads`, `--setup-downloads`, or `--spreadsheet-downloads` replaces the requested, verified workbook families. `--settings-downloads` remains a Matrix compatibility alias. Each option refuses missing, stale, or changed files. A plain publish preserves exact previously published workbook bytes when their recorded source fingerprints remain current; it blocks rather than preserve stale workbooks. `--remove-spreadsheet-downloads` is the explicit removal action.
- `./80 Build/scripts/build-verification-working-copy.sh` generates the machine-local working tracker from current definitions plus `90 Testing/eos_r5_verification_status.yaml`. `import-verification-status.sh` imports approved mutable workbook fields into that Git-tracked YAML. `reconcile-verification-status.sh` preserves history while marking verified results and registration passes for retest when their definition fingerprints changed. The synchronization marker records workbook hashes, the canonical YAML-status hash, workbook revision, and source fingerprint.
- `./80 Build/scripts/open-verification-working-copy.sh` creates the machine-local tracker when neither supported format exists. Before opening an existing copy, it compares file hashes, YAML status, workbook revision, and source fingerprint. It automatically rebuilds only an unchanged stale tracker; it blocks when stale definitions or status coexist with unimported workbook edits. Diagnostics and normal builds direct a safely stale copy to the consolidated refresh command; manual edits continue to require status import. The dedicated on-camera verification workflow documents test order, evidence and completion rules, status import, and YAML-based handoff between Macs.
- `python3 "80 Build/verify_publication.py"` verifies the latest publication commit. Finish-day spreadsheet publication requires both `--require-target matrix` and `--require-target setup`, followed by the ordinary Git synchronization report.
- `python3 "80 Build/release_notes.py"` prints curated reader-facing Markdown for the two most recent publications. `--from VERSION` selects an earlier starting publication through the latest release, `--to VERSION` compares the immediately preceding publication with that release, and both options select an exact historical range. Publication boundaries and dates come from valid committed publish-metadata transitions. Every included target release must have curated highlights in `00 Master/release_notes.yaml`; the command never substitutes commit-message or changed-file guesses.
- A change to an established command, workflow, or operator-facing procedure requires review of the relevant `WORKFLOWS` Markdown and `FINISH_DAY.md`. The change proposal must identify any guide updates or state why none are appropriate. Edit workflow Markdown only; regenerate tracked HTML through the normal build or Finish Day. Finish Day must run and pass source validation, the normal development build, and full validation before it offers staging; validation cannot be postponed while continuing to commit.
- `python3 "80 Build/build.py" <profile>` preserves the existing single-profile workflow; run a full build before publishing.
- `python3 "80 Build/build.py" build website` preserves optional web-host staging behavior; `build pages` refreshes the Pages mirror.
- Do not place rendering decisions in profile YAML or change build logic as a side effect of documentation/content work.

## Output and Release Behavior

References below to **C1 Wildlife**, **C2 Birds in Flight**, and **C3 Landscape** describe the currently approved assignments, not permanently fixed slot names. Matrix and Setup headings must derive from the synchronized C1–C3 mappings. The guarded Cx Foundation assignment transaction may update those headings and matching workflow labels, but concrete registration-row values remain deliberate matrix/tracker inputs and must not be inferred from profile ranges or field guidance.

- Disposable generated artifacts belong in the machine-local workspace's `Build Output/` folder. The default workspace is the sibling folder `<repository name> Local/`; `PRS_LOCAL_WORKSPACE` may set a different absolute or user-relative location.
- `Build Output/merged-build/` is the canonical generated web/PWA bundle. It contains released responsive cards under `Cards/*.html` and copied card assets under `web-assets/`.
- `Build Output/Card Candidates/` is a disposable machine-local review mini-site for unreleased cards. It is not a publishing source and must not be copied into `merged-build`, `docs`, or optional website staging.
- `FINISH_DAY.html` and `WORKFLOWS/*.html` are tracked local project guidance generated from their Markdown sources by normal builds and `finish-day.sh`. They must never be copied into `docs/`.
- `docs/` is an exact publishing mirror for GitHub Pages configured as `main / docs`.
- The version line prepends **Pre-Release •** only at runtime when the generated index is opened from the documented machine-local `Build Output/merged-build/` review location. The identical index opened from `docs/` or served by GitHub Pages retains the published version and date without the indicator.
- The published index orders its sections by expected frequency of use: **Subjects**, **Field Guides**, **Camera Setup & Controls**, then **Deep Dive**.
- `Build Output/website/` is optional staging for non-GitHub web hosts. Only the explicit `build website` target creates or retains it; ordinary full builds remove it. When it exists, validation requires it to match the canonical merged build.
- `Build Output/reports/Subject Settings Matrix.xlsx` is an optional machine-local report. Its primary worksheet starts in canonical card order with Menu Location, Best or Quick Access, and Setting followed by editable C1 Wildlife, C2 Birds in Flight, and C3 Landscape columns initialized from the session-3 camera-body targets, baseline-derived Default Settings, the unchanged authored subject profiles, Card Order, and Rapid Setup Order. The current camera-body registrations were physically verified; exact lens Mode 1/3 remains pending, and any edited target requires physical re-verification. The C1–C3 cells are ordinary values rather than source-switching formulas so they can be edited or replaced during experiments. A separate `C1-C3 Defaults` worksheet preserves the session-3 target table in the same setting order for restoration and repeats the evidence boundary in its note row. Its C1–C3 cells carry transferable relative `not equal` rules and matching hidden helpers so ordinary copy/paste back to the primary sheet restores compatible conditional highlighting instead of replacing it with unformatted cells. The frozen `Compare to:` row provides named-target dropdowns for C1–C3, Default Settings, and every authored subject profile. Every target initially compares with itself, producing an unhighlighted starting view, and may instead compare with any listed target. A frozen `Card starts from:` row immediately below it shows each authored card's `card.field_setup` route, including the starting C1–C3 profile and any named My Menu tab; a subject route with My Menu cues but no Cx foundation begins with **No Cx**, while Default Settings shows its access-only SWITCH and AF Case route without implying a C-mode. Differences use the approved pale-yellow `not equal` conditional highlight through one hidden same-sheet helper column per target; use the cell-comparison rule supported by both Excel and Apple Numbers rather than a custom formula-expression rule. The title, sorting instructions, and legend are three visual bands within one removable drawing object above the primary cell table, so no merged cells interfere with assigning header rows after import into Apple Numbers. The comparison row, card-start row, and table header plus columns A:C are frozen in Excel; the verified Numbers companion uses three native frozen header rows and three native frozen header columns with the banner as a separate object above the table. `C1-C3 Defaults` freezes its note and table-header rows plus column A in both formats. Columns A, B, and C use 85-point, 80-point, and 80-point widths respectively. Column A is normal and left-aligned, column B is bold and centered, column C is bold and right-aligned, and every cell in the table header row is bold. Wrapped table rows use automatic height so all generated content is visible and later user edits resize the rows. Metering is included even though the profiles inherit Evaluative from the baseline. My Menu routes use the `MM-` abbreviation, and only proposed tabs carry an asterisk explained in the legend. Separate numeric sort columns provide canonical card order and rapid camera-setup order.
- `Build Output/reports/EOS R5 Setup & Verification Tracker.xlsx` is the blank publishable Setup master and opens on Dashboard. Its Checklist begins with a removable three-band drawing aligned to the table's left edge, freezes the table header plus column A in Excel, and uses one frozen native header row plus frozen native column A in Numbers. Menu, Checklist, C1–C3 Registration, and Sessions table rows use automatic height so wrapped generated content remains visible and later user-entered notes resize their rows. Fixed heights remain only for structural banner and comparison-control rows; merged title and instruction areas retain deliberate sizing because spreadsheet applications do not reliably auto-fit merged cells. Checklist Status is centered; Menu Location is bold and centered. C1–C3 Registration freezes column A in both formats, right-aligns column A, and materializes complete current values for Default Settings, C1, C2, and C3 during every generation. Column B comes directly from the current baseline; each registered-mode target merges that same baseline with only its explicit slot-specific overrides from `eos_r5_verification_tracker.yaml`, so inherited values cannot remain stale after a baseline change. Its frozen third row keeps `Compare to:` visible in column A and provides named-target dropdowns for Default Settings, C1 Wildlife, C2 Birds in Flight, and C3 Landscape. Default compares with itself; C1–C3 initially compare with Default Settings; every target may instead compare with any listed target, including itself. Target differences use the approved pale-yellow conditional highlight through four narrow same-sheet helper columns that expand with the registration table. Dashboard centers populated values in columns B–E and H and retains formula-driven green, amber, and red status cues. Completion displays 100% as green text, partial completion as bold black text on pale yellow, and 0% as italic text. The Menu sheet is the authoritative workbook lookup for Best Access, Menu Location, and Menu Detail; the Checklist derives those fields by formula. Dedicated My Menu: SWITCH and My Menu: AF Case tests occur at sequences 4 and 5 before shared setup and profile registration; each has independent status and evidence. The AF Case test requires Servo AF, Tracking Sensitivity, Accel./Decel. tracking, and Switching tracked subjects in order. `Backup-Settings` is a completed checkpoint state used after shared setup/controls and after all three registered modes are read back.
- Every Matrix and Setup Excel/Numbers workbook displays its deterministic spreadsheet build ID in the visible banner. The Setup Metadata sheet also records `spreadsheet_build_id`. Prepared and published manifests store the same ID, the website Downloads section displays it beside each family, and publication review/completion reports it. The ID uses a family prefix, workbook revision, and 12-character source fingerprint; it is not the website version.
- A verified Numbers companion and a separate content-hash manifest may accompany each Excel report. Both workbook families visibly show their independent workbook revision, shortened source fingerprint, and generation date. When opt-in replacement publication is authorized, the generated site contains the requested Excel/Numbers pairs under **Downloads** and writes a published release manifest with revisions, source fingerprints, stable filenames, and hashes. Normal local builds automatically include valid prepared workbook families and preserve compatible committed releases for the rest; ordinary publications preserve compatible committed releases unless replacement is explicitly requested. Readiness manifests, verification status, working copies, and import markers are never published.
- On C1–C3 Registration, three-point project-blue outer borders frame the complete column ranges `A:A`, `B:E`, `F:I`, and `J:M`.
- `90 Testing/eos_r5_verification_status.yaml` is the canonical non-published mutable testing record. Spreadsheet import may change only approved Checklist, C1–C3 result/notes, and Sessions fields. Each verified test and passed registration target records the definition fingerprint it verified. Definition changes preserve evidence/history but invalidate affected passes as needing retest; new tests start unverified and removed tests are archived. Excel and Numbers working trackers are prohibited under `90 Testing`; they belong only in the machine-local Verification folder.
- Timestamped pre-change recovery backups belong under the local workspace's `Backups/` folder, not in the repository.
- Card and field-guide PDFs are opt-in.
- Profile and appendix release flags independently control inclusion in the offline bundle as defined by their specifications.
- Validate generated output before publishing. Publishing remains a manual, explicitly authorized Git operation.

## Computer Handoff

- Complete a unit of work on the computer where it began before continuing it elsewhere.
- Run relevant validation, commit every intentional source change, push the current branch, and verify a clean working tree before handoff.
- Import any changed local verification working tracker into Git-tracked YAML status before committing. `finish-day.sh` must block when the workbook differs from its last successful YAML synchronization.
- If a development build changed tracked `docs/` but publication is not intended, restore `docs/` to the current commit before the final clean-tree check. Disposable local output does not transfer through Git and is rebuilt on the next computer.
- Do not run the publishing workflow merely to move work between computers. Publish only when intentionally updating the live site, version, and timestamp.
- `80 Build/scripts/git-status-report.sh` is the read-only project-state report apart from refreshing remote-tracking references with `git fetch --prune`. Unless an explicit expected branch is supplied, it treats the checked-out branch as the intended branch and requires that branch to track its exact same-named branch on `origin`. It must not pull, merge, commit, push, switch branches, or change project files.
- `80 Build/scripts/preflight-git.sh` uses that report to allow clean synchronized work or identified local work on either `main` or a deliberate prototype branch, and to block a clone that is behind, diverged, detached, missing its exact matching upstream, or cannot be verified safely. It must not update the working branch automatically.
- `80 Build/scripts/finish-day.sh` is the interactive terminal interface to the same guarded Finish Day engine used by Profile Editor. Both interfaces run source-only validation, the normal development build, and full validation in that order after preparation approval. They require separate approval for commit and push. When a development build changes `docs/`, the shared engine creates a timestamped machine-local recovery archive, restores tracked `docs/` to `HEAD`, removes only archived untracked generated files under `docs/`, verifies that `docs/` is clean, and then offers the remaining source changes for exact review. It must refuse to push when an existing unpushed commit contains `docs/` changes, and it must never invoke the publishing workflow.

## Validation Requirements

Run `python3 "80 Build/validator.py"` after relevant changes. It orchestrates validators for:

- project structure (`validators/structure.py`);
- YAML parseability and duplicate keys (`yaml_validator.py`);
- baseline shape (`baseline_validator.py`);
- card-layout structure and required-setting alignment (`card_layout_validator.py`);
- complete, unique access methods and rapid-setup ordering for every subject-summary setting (`setting_access_validator.py`);
- external spreadsheet layout/source requirements (`spreadsheet_spec_validator.py`);
- consistency of prepared workbook-download manifests, published release fingerprints/hashes, and any generated site downloads (`spreadsheet_download_validator.py`);
- canonical verification-status structure and agreement between Verified results and current definition fingerprints (`verification_status_validator.py`);
- curated release-note source structure (`release_notes_validator.py`);
- governing-document presence, local links, stale retired references, and decision statuses (`governance_validator.py`);
